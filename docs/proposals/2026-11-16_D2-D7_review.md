## 1. Most important new findings

1. **[V] The benchmark's own labels disagree across files.** The top-level index `bug_replication/README.md` agrees with [RP] `607_defects_types.csv` for all 110 defects. However, the per-project READMEs give a different type or subtype for **22 defects**, some using names that are not in the 13-subtype taxonomy at all (e.g. "Authorization and Permission Handling Errors", "Runtime Errors and Exception Handling", "Functional Defect"). → The authoritative labels are the top-level index / [RP] CSV.
2. **[V] Our earlier type tally (E4) used the type column, which is internally inconsistent for one defect.** `kafka-rest#475` is typed T6 but its subtype is ST5 (a T2 subtype). Counted by subtype, the 110 are: **T2 60, T1 25, T4 10, T5 9, T3 4, T6 2.** E4 said T2 59 / T6 3.
3. **[V] All 16 RESTCountries defects are wrong values in a data file.** Every patch changes only `countriesV2.json`/`countriesV1.json` (CSV `patched_file_types` = `data-file`). The benchmark nevertheless labels 12 of them ST5 (query filter) and 4 ST3 (environment configuration). This is direct evidence for risk R1 (label ≠ detection mechanism).
4. **[V] Two RESTCountries ground-truth problems.**
   - `#237`'s patch commit `6302b10` ("Added Nepal as border to China") actually adds NPL to **Taiwan's** borders. China's borders are identical at buggy and patched SHAs, so the documented behaviour is *not* fixed in the patched version.
   - `#199`'s first patch SHA (the CLI default for `--patched`) only edits `countriesV1.json`, while the README triggers `/v2/all`. The v2 fix is patch 2 (`8ec4d03`).
5. **[V] The provided specs carry little field-level information.**
   - RESTCountries spec: 10 GET operations, **no response schemas**, and a wrong server URL.
   - Dolibarr specs: Swagger 2.0 from the Restler API explorer; request bodies are an opaque `request_data` object and many GET responses are typed `string`.
   - → A purely spec-based feature extractor will see operations and parameters, but almost no response fields.
6. **[V] Some specs leak or mismatch.**
   - `enviroCar-server#45_spec.yaml` contains "WARNING - BUG #45" and "BUG - causes StackOverflowError!".
   - Every spec **filename** contains the issue number.
   - Dolibarr has 6 different specs across 24 defects; the `#26066` variant is the only one listing `/multicurrencies` (its triggering endpoint).
   - For several Dolibarr defects the triggering endpoint is missing from the spec provided for that defect (heuristic check).
7. **[V] Dolibarr setup is mostly manual.**
   - The deploy script contains a function that would enable the API and grant permissions (`configure_api_and_modules`), but **nothing calls it**.
   - The installer wizard, API key and any bug-specific configuration must be done by hand.
   - The replication READMEs hard-code personal API keys.
   - Several READMEs use extra fields or module settings that their steps never create.
8. **[V] Pilot data problems in Dolibarr.**
   - `#26307` has no replication folder or spec, although the deploy script and the CSV support it.
   - `#23345`'s README is empty (0 bytes).
   - `#29372` reproduces through a UI page (`holiday/month_report.php`), not the REST API.
9. **[V] Overlap with the paper's 30-defect RQ3 sample is 8 (2 RESTCountries + 6 Dolibarr), but only 6 are usable.** The RQ3 sample also contains two defects outside the 110 (`podman#14676`, `signal-cli-rest-api#103`).
10. **[V] Closest new related work.** [TV26] embeds a (mutation) taxonomy in LLM prompts for robustness testing. It does not select strategies from API features, does not use an empirical defect taxonomy, and uses a 5xx oracle. It must be cited, and it is not a substitute for the focused novelty check.
11. **[A] Researcher exposure.** By auditing RESTCountries and Dolibarr in detail we (including this review) have now read their ground truth. These should be treated as **development/pilot** defects; the headline evaluation should use defects whose replication material the strategy designers have not studied (see §8, Q7).

## 2. D2 — Defects4REST taxonomy

### Evaluation

| Question | Finding |
|---|---|
| Is it a good reference vocabulary? | **Yes** [V]: empirically derived (607 issues, 50 projects), peer-reviewed, and the benchmark uses the same labels. |
| How were labels assigned? | [V] [P] §3.3.3: each issue was assigned its *dominant* subtype, "the primary manifestation observed in the issue report and its corresponding patch". So a label describes the reported symptom/fix area, not how a test can detect it. |
| Are labels reliable at defect level? | [V] Top-level index = [RP] CSV for 110/110; per-project READMEs disagree for 22. Use the index/CSV and pin the commit. |
| Has anyone mapped the taxonomy to testing before? | [V] Yes, partly: [P] Table 7 maps each subtype to EvoMaster fault classes from [M22] (mapped / partially mapped / unmapped). Our mapping must cite it and differ: we map to **observable features and test strategies**, not to fault classes of one tool. |
| Novelty risk | Adopting the taxonomy is *not* a contribution. Embedding a taxonomy in prompts is also not new ([TV26]). |

### How we can build our own mapping (defect category → observable features → strategies)

1. **Start from the taxonomy and the paper's failure analysis**, not from the pilot defects. Inputs: subtype definitions [P Table 4], [P Table 7], limitations L1–L9 [P §4.3.2], generic REST testing knowledge. *Do not use the pilot READMEs to add or tune strategies* (§1 item 11).
2. For each subtype, write down: (a) how it would manifest at the HTTP interface, (b) which observable features signal that an operation could exhibit it, (c) which test strategy probes it, (d) which oracle decides pass/fail.
3. Record each mapping row with a rationale and a source (paper section or general testing practice). Freeze and version it before any evaluation run.
4. Separately and **only for analysis**, have two people annotate each evaluated defect with its *detection mechanism* (oracle class, see §3) after runs. This gives a second, mechanism-based view of the same defects to test R1 directly, and is a citable artefact of our own.

### Which categories can realistically be targeted with information available before testing

| Subtype (authoritative) | # in 110 [V] | Targetable black-box from spec/docs? [A] | Why |
|---|---|---|---|

### Revised recommendation [R]

Adopt the Defects4REST taxonomy (6 types / 13 subtypes, authoritative labels from the top-level index = [RP] CSV, pinned commit) as the **reference vocabulary for organising the strategy catalogue, stratifying the sample and reporting results**. Do not feed per-defect labels to the system. Our own contribution is the explicit, frozen mapping from observable API features to test strategies (D3) and its empirical evaluation. Report the label inconsistencies found.

**Strategies that span several defect types** (evidence that type ≠ strategy) [V for labels, A for reachability]:
- **S3 round-trip** reaches Dolibarr defects labelled ST4 (23179, 31369, 31677, 33949), ST3 (29115, 30432), ST2 (30950) and ST8 (32072).
- **S4** reaches ST4 (29421, 32111) and ST5 (29424, 30161).
- **S7** reaches ST4 and ST5.
- **S8** reaches every RESTCountries defect regardless of its ST3/ST5 label.

**Selector design and leakage guarantees [R]**
- **Input:** a feature record extracted from the allowed inputs only (§5). Output: an ordered list of strategies, a budget share per strategy, and a logged reason for each.
- **Defect-blind by construction:** the selector runs once per *(subject, spec, arm, seed)*. It never receives a defect ID, label, or triggering endpoint, and its code cannot import benchmark metadata (enforced allow-list, §5).
- **Feature sources:** decide whether S7/S8 may use runtime observations. A bounded "probe" phase that calls each GET operation once, identical for both arms, would supply response fields. Otherwise S7/S8 cannot be triggered from the RESTCountries spec at all (it has no response schemas). → open question Q2.

### Revised recommendation [R]

Keep D3, adding three things: (a) the strategy catalogue above (to be finalised before evaluation, derived from the taxonomy and [P] L1–L9, not from pilot READMEs); (b) the defect-blind selector contract; (c) the post-hoc *detection-mechanism* annotation used only in analysis.

## 4. D4 — Differential detection protocol (refined)

**Facts that shape the protocol [V]**
- `defects4rest checkout` deploys one version at a time. Buggy and patched use the same container names and port 8080, and deploying stops running services. → replay is **sequential**, not side-by-side.
- `--patched` takes an index (default 1); several defects have more than one patch SHA (e.g. RESTCountries #199 has 3). The index must be chosen and recorded per defect.
- RESTCountries data is static, so responses should be deterministic [A]. Dolibarr creates auto-increment IDs, timestamps (`date_creation`, `tms`) and provisional refs (`(PROV54)`), so raw responses are not comparable across deployments.
- Dolibarr keeps its DB in a Docker volume; only `--clean` removes volumes.

### Protocol

1. **Freeze the test suite** for each (subject, spec, arm, seed) before any execution. Serialise it (requests, sequences, variable bindings, assertions) and record its SHA-256.
2. **Pre-run benchmark validation** (once per defect, by a researcher, outside the system): reproduce the README's triggering behaviour on buggy *and* check the expected behaviour on patched. Defects failing this check (e.g. RESTCountries #237) are excluded *before* any arm is run, and listed.
3. **Replay loop per defect and version (buggy, then patched):**
   1. `--clean` → deploy → health check (a fixed request must return 2xx within a timeout).
   2. Apply the **fixture**: a defect-independent setup script that is identical for every defect of a subject (e.g. Dolibarr: complete installer, create admin API key, optionally a fixed read-only second user). Record a hash of the DB state after the fixture if feasible.
   3. Run the frozen suite **r times** (proposal: r = 3), with a clean state before each repetition if the suite writes data.
   4. Capture every request/response, timing, container image IDs/digests, and the commit checked out.
4. **Authentication:** the runner injects credentials from the fixture config. The generator only learns that an API-key scheme exists, as declared in the spec. Role-variation tests (S6) refer to symbolic roles (`admin`, `reader`) resolved by the runner.
5. **Non-determinism controls:**
   - Bind IDs/refs captured from responses to variables; never hard-code them.
   - Do not assert on volatile fields (timestamps, auto refs) unless the assertion is relational, e.g. "value read = value written".
   - A test is **stable** on a version only if it gives the same verdict in all r runs. Unstable tests are reported as flaky and excluded from detection.
6. **Outcome classes per test per version:**

   | Class | Meaning | Counts toward detection? |
   |---|---|---|
   | PASS | all assertions hold | — |
   | FAIL | an assertion fails with a valid HTTP exchange | candidate |
   | ERROR-INFRA | deploy failure, health check failure, connection refused/reset, timeout, proxy 502/503 | **never**; rerun the deployment up to 2×, then mark the defect *not evaluable* for that run |
   | ERROR-TEST | test is malformed: unresolved variable, unparsable request, missing prerequisite created by the test itself | **never**; reported as invalid tests |
   | FLAKY | different verdicts across the r runs on the same version | **never**; reported |

7. **Candidate detection** for (test t, defect d): t is stable FAIL on buggy and stable PASS on patched, with no ERROR-INFRA in either.
8. **Manual confirmation** of each candidate, blind to arm (arm labels hidden). Reviewers *may* read the replication README at this stage, which is analysis, not generation. Verdicts:
   - **Confirmed:** the failure is the documented defect.
   - **Related:** same root cause, different manifestation (counted separately; report sensitivity both ways).
   - **Unrelated:** the buggy and patched versions differ for another reason, e.g. other commits between them.
   - **Spurious:** environment or non-determinism missed by the checks.

   Record per candidate: defect ID, test ID and hash, failing request/response on buggy, response on patched, the failing assertion, verdict, rationale, reviewer, date. Two reviewers on all candidates, or at least a random 30% double-coded, with Cohen's κ reported.
9. **Defect detected by an arm/seed** ⇔ at least one Confirmed candidate.
10. **Report alongside detections:** stable FAILs on the patched version (false-positive proxy), ERROR-INFRA and not-evaluable counts, flaky counts.

[G20] reports the same practical issues in REST differential testing (abstracting trivial differences, non-determinism). Cite it when describing the oracle.

### Revised recommendation [R]

Keep the three-part oracle (fail on buggy, pass on patched, human confirmation). Add: pre-run validation of each defect's ground truth, a defect-independent fixture, r repeated runs with flakiness exclusion, explicit outcome classes that keep infrastructure and test errors out of detections, a recorded patch index, and a blind confirmation record.

## 5. D5 — Leakage prevention

### 5.1 Where hidden defect information lives [V]

| Location | Contents | Risk |
|---|---|---|
| `bug_replication/README.md` | all 110 IDs, issue links, type, subtype | labels |
| `bug_replication/<project>/README.md` | per-defect description and (inconsistent) labels | labels, symptom |
| `bug_replication/<p>/<p>#<id>/README.md` | description, issue URL, **triggering endpoints**, exact requests, buggy vs expected responses | full ground truth |
| `bug_replication/**/img/*` | screenshots (e.g. dolibarr#29372) | ground truth |
| `defects4rest/data/defect_data/*_info.csv` | issue title/body, `patched_file_types`, `text_for_topic_modeling`, classifier prediction, buggy/patch SHAs, patched files, days to fix, docker versions | full ground truth |
| `defects4rest/src/deployment_scripts/*.py`, `api_dep_setup/*.py` | per-issue branches and hooks (RC #235 fork, Dolibarr #26307 PHP 8.1, `issue_<n>` seeding functions for nocodb, netbox, kafka-rest, mastodon, seaweedfs, Podman rootless list) | reveals which defects need special setup or seed data |
| `defects4rest info` output; `checkout` console output | issue number, SHA, URLs | ID, SHA |
| Port convention in `BugRow` (`80{bug_id}` / `81{bug_id}`) | port encodes the CSV bug ID where used | weak |
| Cloned upstream repo under the CLI's temp project dir | full git history, including the **fix commit and its message** (e.g. RC 6302b10 "Fixing …/issues/237") | full ground truth |
| [RP] (607 CSVs with rationale, RQ3 report, tool logs) | labels, triggering behaviour | full ground truth |
| Upstream issue trackers and public web | issue text | contamination (model may have seen it) |
| **Spec files** | filename contains the issue number; `enviroCar-server#45` spec text names the bug; per-defect spec variants (Dolibarr: 6 distinct specs across 24 defects) | direct or indirect leak |

### 5.2 Can defect-specific specifications reveal the target endpoint? [V]

- **Spec identity:** RESTCountries uses one identical spec for all 16 defects, so it cannot single out a defect. Dolibarr: 19 defects share one spec; `#23415`, `#24661`, `#26066`, `#32111`, `#33949` each have their own.
- **Version evolution, mostly:** most variant differences look like version changes, e.g. `/recruitment/…` → `/recruitments/…` and `/partnershipapi/…` → `/partnerships/…` [A: inferred from the rename pattern].
- **But one variant points at its defect:** `#26066`'s variant is the base spec **plus 12 paths**, including the four `/multicurrencies` paths; `/multicurrencies` is its triggering endpoint. The Restler explorer lists only enabled modules, so the module set used to generate a spec can reveal where the defect is [A: mechanism inferred].
- **Spec–version mismatch:** a heuristic match found the README's triggering endpoint missing from that defect's provided spec for Dolibarr `#29421` (the spec has `/memberstypes/{id}`, the README uses `/members/types/{id}`), and partly missing for `#26881`, `#30950`, `#31677`, `#32145`, `#33689`. So one shared spec does not match every deployed version.
- **Explicit text:** `enviroCar-server#45_spec.yaml` contains explicit bug text. It is not a pilot subject, but the same scan must run on every spec we use.

### 5.3 Input allow-list [R]

The selector and generator may receive **only**:
1. A **sanitised spec copy** with a neutral filename (e.g. `spec.json`; never `<project>#<issue>`), produced by a fixed procedure:
   - **RESTCountries:** the shared spec.
   - **Dolibarr:** either one spec per subject chosen without reference to any defect, or a spec regenerated from each deployed buggy instance with a fixed, defect-independent module configuration (Q8).
   - A keyword scan (`bug`, `issue #`, `fix`, `buggy`, `patched`, `workaround`, `regression`) plus manual review before use.
2. Genuinely public API documentation for the subject, collected once per subject (URL + date + hash). It must not come from issue trackers.
3. The base URL and symbolic auth scheme, from runner config.
4. *(If Q2 is approved)* responses from the fixed probe phase, identical for both arms.

Everything in §5.1 is forbidden. The generator runs in a working directory that contains only the allowed files and has no network access except the LLM API. The LLM is never told the project issue number, the defect ID, or which endpoint is being evaluated.

### 5.4 Logging every input [R]

- **Run manifest:** each generation run writes `manifest.json` containing:
  - every file read: path, size, SHA-256, allow-list rule matched;
  - selector features and output with reasons;
  - every LLM call: full prompt and response stored, model ID/version, provider, temperature/seed, tokens;
  - git commit of our code, benchmark commit, timestamps.
- **Enforcement in code:** a single input-loader component is the only way to read files. It rejects any path not on the allow-list and fails the run, not just logs a warning. A CI test asserts that the selector and generator packages contain no imports of benchmark-metadata readers.
- **Audit:** before each experiment batch, a script greps all stored prompts for defect IDs, issue URLs and triggering-endpoint strings that the spec does not legitimately contain. Any hit voids the run.

### 5.5 Not receiving the target because a defect is being evaluated [R]

Generate **per subject and spec, not per defect**, then replay the frozen suite against every defect deployment (§4).
- **RESTCountries:** one spec, so one suite per arm and seed covers all 16 defects.
- **Dolibarr:** the unit is the chosen spec. If specs are regenerated per version, the procedure is the same for every version and receives no defect information.

## 6. D6 — Prevalence priors

### Comparison

| | Feature-based deterministic selection | Prevalence-weighted selection |
|---|---|---|
| Input | observable features only | features + historical type frequencies |
| Leakage/circularity | none | must exclude evaluation projects (D6) |
| Effect size of exclusion | — | small for the pilot [V]: T2 41.7% → 39.7%, T1 27.0% → 27.2% when RESTCountries (16) and Dolibarr (29) are removed from the 607 |
| Mapping problem | — | priors are over **defect types**, but strategies cut across types (§3), so the conversion from type priors to strategy weights is itself a tunable design choice |
| Fit to benchmark | — | per-type frequencies in the 110 differ from the 607 (e.g. ST5 is 35/110 = 32% of the executable set vs 118/607 = 19% of the dataset) [V] |
| Explainability | high | lower (two sources of priority) |
| Extra tunable parts | none | weight-conversion rule, smoothing |

### Revised recommendation [R]

**Exclude prevalence priors from the initial system.** The proposed arm uses feature-triggered strategies from the taxonomy-derived catalogue with a fixed, pre-registered ordering and an equal budget split among triggered strategies. Keep prevalence weighting as a **later ablation**, computed from the 607 excluding all evaluation projects. This is the simplest defensible design: no circularity, no extra tuning.

Consequence for the claim: the "taxonomy guidance" then lies in the *catalogue and mapping* (which strategies exist, which features trigger them, coverage of all subtypes), not in frequencies. This sharpens Q1: we need a way to tell taxonomy guidance apart from plain "structured strategy prompting".

### 7.4 Revised recommendation [R]

- **First pilot subject: RESTCountries, as a pipeline and oracle shake-down, not as main evidence.**
  - Use 15 defects: exclude #237; use `--patched 2` for #199; flag #202 as contested.
  - Goal: prove deploy → generate → replay → differential verdict → confirmation end to end, cheaply and deterministically.
  - Report it separately, because it mainly measures LLM world knowledge.
- **Conditional second subject: Dolibarr**, proceeding only if all three conditions hold:
  - (a) the installer, API key and a defect-independent fixture can be scripted and repeated per deployment within a stated time budget;
  - (b) a defect-blind spec procedure is chosen (Q8);
  - (c) at least one Dolibarr defect reproduces on buggy and not on patched, done manually first.

  Dolibarr is the subject that actually exercises strategy diversity.
- **Fallbacks** if Dolibarr fails (a): NetBox (6) or NocoDB (6), per the earlier decision. Their per-issue seed hooks in `api_dep_setup` must be reviewed for leakage first (§5.1).
- **Headline evaluation:** run it on defects whose replication material the strategy designers have not studied (Q7). RESTCountries and Dolibarr become the development set.

## 8. Unresolved research questions

1. **Attribution:** if the proposed arm wins, is it because of the taxonomy or because of structured strategy prompting in general? Options: add an ablation arm (same strategies without the taxonomy-derived mapping/coverage), or define the contribution as "the taxonomy-derived catalogue + feature mapping" and argue it.
2. **Feature sources:** may features include responses from a bounded, arm-shared probe phase? Without it, S7/S8 cannot be triggered from RESTCountries. With it, generation interacts with the faulty implementation, which can make tests adapt to wrong behaviour ([RTB]).
3. **Unit of generation:** per subject/spec (recommended) vs per defect deployment. This affects budget accounting and leakage.
4. **Dolibarr automation:** can the installer and API key setup be scripted per version? What is the hands-on time per deployment × 2 versions × r repetitions?
5. **World-knowledge defects:** include RESTCountries in the main analysis, or only as a separate stratum?
6. **Benchmark defects:** freeze the exclusion rules (#237, #26307, #23345, #29372, specs missing triggering endpoints) and decide whether to report the issues to the maintainers.
7. **Held-out evaluation set:** which projects (e.g. NetBox, NocoDB, mastodon, awx, flowable), how many defects, and how to stay blind to their READMEs while building the fixtures they need?
8. **Dolibarr spec procedure:** use the provided per-defect spec, one project-level spec, or regenerate per version with a fixed module set?
9. **Repetitions:** the values of r, the number of seeds, and the flakiness rule.
10. **Budget unit:** LLM tokens, LLM calls, HTTP requests, or wall-clock — and which one is held equal.
11. **Confirmation logistics:** who are the two reviewers, and can arm-blinding be enforced in practice?
12. **Model and contamination:** RESTCountries issues (e.g. "Kiev → Kyiv") are widely known. Which model and version, and how do we report contamination risk?
13. **Novelty:** the focused prior-art check is still pending. [TV26] is now a must-cite neighbour.

## 9. Threats to validity identified in this review

- **Construct:** benchmark labels describe the reported symptom/fix area (single dominant subtype), not the detection mechanism. Per-project labels are inconsistent (22/110).
- **Construct:** some ground truth is flawed (#237, #199 patch index) and some specs mismatch their versions.
- **Internal:** researcher exposure to pilot ground truth can bias the strategy design. Mitigate with a frozen catalogue and held-out evaluation defects.
- **Internal:** possible leakage through spec filenames, spec text and spec variants; the cloned upstream repo contains fix commits.
- **Internal:** manual Dolibarr setup introduces operator variability between deployments.
- **External:** the pilot subjects are dominated by T2/ST4–ST5. RESTCountries is a single-mechanism dataset.
- **Statistical:** small samples (≈15 + ≈18–22 pilot defects). No per-type significance claims possible.
